# 设计依据与微信上架核验清单

## 从胜负欲出发，为什么这样设计

不采用需要实时双人对战的方案：微信社交链好友互相在线的时机不可控，匹配与反作弊又需要后端及运营。`75 秒独立挑战 + 同日同种子 + 好友纪录` 把“我能不能超过你”变成低门槛的短循环。玩家有足够长的战术窗口学会 8 秒延迟的回声，在下一局利用过去的路线修正决策。

本质是单机技能向计分竞技，与平台广告没有属性挂钩：

1. **第 0–8 秒**：熟悉移动、能量和冲刺；系统开始记录路径。
2. **第 8–20 秒**：回声进入场景，玩家第一次发现“过去的自己会帮我拾取”的反馈。
3. **第 20–50 秒**：怪物密度增加，可规划双核装置，让回声与现在的自己合作；不同处理方式形成分差。
4. **第 50–75 秒**：满能量超载时，双倍收益与加速怪物形成取舍；连续拾取维持连击更有风险。
5. **结算**：展示最高分、最长连击、好友榜入口和明确的“发起挑战”入口；再来一次成本极低。

**假设而非已验证事实**：75 秒长度是否更优、回声是否清晰易懂、复玩率是否高、竞技传播是否能带来自然裂变。必须实测：教程完成率、平均局数、首次 8 秒后存活率、次日回访、主动分享与通过分享启动占比、广告完整观看/异常回调。

## 社交机制边界

- 开放数据域的读取接口在主域不可访问；只能通过主域向 `wx.getOpenDataContext().postMessage(...)` 发送 `day`，在 `openDataContext/index.js` 内部调 `wx.getFriendCloudStorage()`，画到 `sharedCanvas`，再由主域 `SubContextView` 展示。
- 用户成绩从主域的 `wx.setUserCloudStorage()` 上传日期和分数（不主动读取好友数据）；开放数据域按当天日期过滤，并显示昵称/头像。微信后台的相关隐私声明和接口授权必须真实具备，设置项默认 `false`。
- 仅展示已有好友云存储记录；小游戏主域不调用社交关系的原始数据。
- 微信分享将 `day`、`target` 写入启动参数，接收方看到一个分数目标。**不因分享次数、好友点击或群转发直接解锁内容/奖励**，避免诱导分享。
- 本实现客户端分数可被篡改，没有签名服务端、没有回放审计，也没有跨设备永久全服榜单。面向小型原型可试运行，但不适合现金奖励的正式竞赛。

## 广告边界

- Banner：仅结算界面尝试展示；不要覆盖可点击选项和系统安全区（不同设备测试）。
- 插屏：每 3 局、仅结算流程尝试展示；服务端/微信可能限频，显示失败不影响游戏。
- 激励视频：主动点击，真实回调 `isEnded===true` 才给纯外观货币；提前关闭、加载错误、重复回调不给重复奖励。
- 一切广告 ID 留空；用户必须有正式流量主权限及真实广告位。不能用微信测试号模拟正式盈利。

## 微信构建与版本核验

- [ ] 通过 Cocos Creator 3.8.8 成功打开 `Main.scene`，所有脚本、PNG、WAV 正常导入，控制台零阻断错误。
- [ ] 启动场景 `Main`、竖屏 Portrait、设计分辨率 750 × 1334，触控和机型安全区确认。
- [ ] 微信小游戏 build 成功；运行 `npm run postbuild -- build/wechatgame`，验证 `game.json` 和 `openDataContext/index.js` 均存在。
- [ ] 在微信开发者工具首次进入、重新进入、关卡计时、暂停恢复、切回前台、跨天、清除存储；不能卡死或掉帧严重。
- [ ] 两个真实微信好友账号上传分数，同一天好友榜排序正确；不同日旧分数不显示；没有假数据；失败有明确状态。
- [ ] 好友分享进入能够看到原目标分数，不强制再转发，不因分享免费获取数值优势。
- [ ] 激励视频完整播放给一次装饰币；中途退出不发；广告错误不发；短时间连续点击不会多领。
- [ ] 低端安卓、旧 iPhone：60 Hz / 30 Hz、内存、音频自动播放限制、触控方向、适配、启动时间、滑动冲突。
- [ ] 实际微信构建主包 **不超过 4 MB**，超过则优化引擎模块/纹理/音频和分包；不能把这个工程的源码 ZIP 大小当成最终包体。
- [ ] 正式 AppID、适用隐私政策及使用声明、备案、素材版权、网络权限、微信平台审核、广告权限逐项真实确认。
